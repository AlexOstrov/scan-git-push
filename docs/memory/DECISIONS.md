# DECISIONS

## Режим `scan` (редакция 3 `dop_tz01.md`)

- Отдельная БД `db/scan.db`; `analysis.db` не затрагивается.
- Миграции не предусмотрены: схема создаётся с нуля с версией `3`; при версии схемы `≠ 3` (включая `1`, `2`) или повреждении — код `12` с подсказкой удалить БД и пересоздать.
- Содержимое файлов **не хранится**: только `file_hash(hash, size_bytes)` + `file_snapshot` + `point_content` (вхождение маркера). Хэш — единственный след содержимого.
- Все параметры режима вложены в корневой объект `SCAN` (`SCAN.GIT_PROJECTS`, `SCAN.INCLUDE`, ...); плоские `SCAN_*` не используются.
- Область сканирования по умолчанию — только `*.txt` и `*.md`; `SCAN.EXCLUDE` и `SCAN.EXCLUDE_SECRETS` по умолчанию пусты.
- Четыре PRAGMA: `foreign_keys = ON`, `journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 5000`. `synchronous` задаётся до начала транзакции.
- Несколько git-проектов (`SCAN.GIT_PROJECTS`): своё зеркало и свой `scan_run` на проект, обработка последовательная, транзакция на проект.
- `req.code` уникален **в разрезе всех проектов** (`UNIQUE(code)`); одинаковые `id` и `point` в разных проектах — одно требование и один раздел. Привязка к проекту/ветке/коммиту/файлу — через `point_content → file_snapshot → git_project`.
- Завершающая точка в `point` игнорируется (`5.5.1.` == `5.5.1`); `point="."` — ошибка. Это потребовало поднять `SCAN_PARSER_VERSION` до `2`, чтобы переразобрать неизменённые файлы.
- Одинаковые `(id, point)` в разных проектах, разных файлах и на разных строках — не дубликаты; сохраняются все вхождения.
- Поддерживается только канонический маркер `<!-- REQ-META ... -->`; legacy-форматы (`ID_REQ`, `ID_EXAMPLE`, вариант без `-->`) удалены — по ним выводится предупреждение `[WARN] legacy marker format`.
- Вместо `TRUNCATE` — UPSERT и reconciliation; повторный запуск идемпотентен. Reconciliation глобальна: требование/раздел активны, пока есть вхождение хотя бы в одном проекте.
- Доступ к git — через локальное зеркало (`git clone --mirror`), а не GitHub Contents API.
- Коды выхода: `5` — репозиторий (все проекты недоступны), `9` — БД, `10` — strict-валидация, `11` — частичный сбой, `12` — схема. Приоритет: `12` → `9` → `5` → `11` → `10` → `0`.
- `scan` не вызывает LLM и не требует LLM-токенов.
- Выбор веток: `--branch` → `--all-branches` → `SCAN.BRANCHES` (`all`, `default`, список); затем применяются `BRANCH_INCLUDE`/`BRANCH_EXCLUDE`; порядок сортируется для детерминированного разрешения конфликтов имён.
- `scan_run` фиксирует каждый прогон: активный `running` блокирует новый запуск, `--force` помечает его `failed`; `running` старше 24 часов считается зависшим.
- Логи `scan` пишутся в `SCAN.LOG_PATH` (DEBUG), консоль получает вывод только с `--verbose`; `--json` печатает результат в stdout, человекочитаемая сводка уходит в stderr.
- Прогресс: Rich progress bar только при интерактивном TTY; `--json` и перенаправленный вывод его отключают, чтобы не засорять stdout.
- Сбой `git log` при построении карты последних коммитов считается частичной ошибкой (`partial`, код `11`); файлы сохраняются без метаданных коммита.
- `report-from-db --req` формирует автономный HTML «Отчет по требованиям и разделам» из `scan.db` (только активные требования/разделы), с группировкой требование → раздел и естественной сортировкой; `analysis.db` и LLM не нужны. Файл: `reports/requirements_YYYYMMDD.html`.
- `req.is_export` / `point.is_export` (`0` по умолчанию, `1` — экспорт выполнен). Инвалидация — SQLite-триггерами в схеме, а не в коде сканера: изменение `req.code/name/status`, `point.point/status`, вставка/изменение/удаление `point_content`. Условие `NEW.x IS NOT OLD.x` не даёт сбрасывать флаг при повторном сканировании без изменений; `UPDATE OF` не включает `is_export`, поэтому будущий экспорт может выставить `1` без самосброса.
- `replace_occurrences` — diff, а не delete+reinsert: неизменённые вхождения сохраняют номерные поля и `is_export`; триггеры срабатывают только на реальные изменения.
- `point_content.numbeartefact`, `numbercase`, `numberscenario`, `numberstep` — `TEXT DEFAULT NULL`; заполнение и экспорт — будущая доработка.
- Версия схемы `scan.db` поднята до `3`, потому что изменился DDL. Миграции по-прежнему не поддерживаются: БД v2 нужно удалить и пересоздать (код `12`).

## Основной режим (ТЗ v2, 01.11.2026)

- `GIT_PROJECT` удалён: проекты задаются только в `SCAN.GIT_PROJECTS` или через `--project`. Плоский конфиг 0.1 однократно транслируется, но `GIT_PROJECT` вместе с секциями — ошибка.
- Источник данных — локальные bare-зеркала в `SCAN.MIRROR_DIR`; путь `<repo>-<sha256(url_key)[:10]>.git`. `MIRROR_FILTER=auto` включает `--filter=blob:none` для remote и полный клон для локальных путей.
- Анализируются все ветки (`ANALYSIS.BRANCHES=all`), без merge-коммитов, по committer date (`%cI`, `git log --since`). Дедупликация SHA — силами `git log`.
- `analysis.db` — схема версии `1`; ключ `(git_project_id, sha)`; legacy-БД мигрирует один раз с бэкапом `analysis.db.bak`; версия ≠ 1 → код `12`.
- `commit_date`/`author_date` нормализуются в UTC: `%cI` приходит с локальным офсетом, а `get_analyses`/`cleanup_old_records` сравнивают строки лексикографически. Нормализация выполняется при разборе (`rev._parse_date`), при записи (`_to_utc_iso`) и один раз для существующих строк в `initialize()` (`_normalize_commit_dates`, без смены версии схемы).
- `url_key` одинаков в `scan.db` и `analysis.db`: remote — `host/path` без схемы/учётных данных/`.git`, local — абсолютный POSIX-путь. Это ключ для `ATTACH` и `LINK_REQUIREMENTS`.
- Отчёты всегда генерируются из БД за период; повторный запуск без новых коммитов даёт непустой отчёт. Дополнительно формируется сводный `_summary_{date}`.
- LLM-провайдеры только `ollama` и `mistral`; `github_models` и `groq` удалены из кода, зависимостей и конфига.
- `LINK_REQUIREMENTS` включён в эту итерацию: read-only подключение к `scan.db`, отсутствие БД не прерывает анализ.
- `ANALYSIS.EXCLUDE` по умолчанию: lock-файлы, `*.min.js`, `*.min.css`, `*.map`, `dist/**`, `build/**`, `vendor/**`, `node_modules/**`, `.git/**`.
- Проверки: 114 тестов на временных git-репозиториях; сквозной пайплайн (`check_pipeline.py`) — exit 0.
- Имя проектного отчёта включает `sha256(url_key)[:6]`: суффикс добавляется всегда, поэтому два проекта с одинаковым коротким именем не перезаписывают отчёты друг друга.
- Таймауты LLM раздельные: `OLLAMA_HTTP_TIMEOUT` (180 с) для локальной Ollama, `HTTP_TIMEOUT` (30 с) для Mistral. Общий 30-секундный лимит обрывал большие чанки на CPU.
- `ANALYSIS.CONCURRENCY` удалён: поле не использовалось ни в одном обработчике; анализ остаётся последовательным.
- Ошибки проектов в `analyze --json` проходят через `redact_credentials()` — URL с учётными данными не попадают в JSON и консоль.
- Приоритет кодов анализа: `12` → `9` → (нет проектов: `2` при auth, иначе `5`) → `11` → `0`; auth-сбой одного проекта при успехе остальных даёт `11`.
- Ретенция `analysis.db` удаляет записи по `commit_date`; если `--days` больше `DB_RETENTION_DAYS`, отчёт неполный, но завершается кодом `0`.
