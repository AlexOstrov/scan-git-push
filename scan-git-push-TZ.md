# Техническое задание: Скрининг git push проекта с LLM-анализатором содержимого

---

## 1. Цель проекта

Разработать Python-утилиту, выполняющую анализ git push изменений указанного проекта за указанное количество дней. К анализу подключается LLM-модель (Ollama или Mistral AI), проводящая анализ содержимого и выдающая результирующее саммари в консоль, Markdown и интерактивный HTML-отчёт.

> **Примечание (21.10.2026):** GitHub Models API закрыт 30.07.2026. Groq недоступен в РФ (403 Forbidden, обход запрещён §4.1 Terms of Use). В качестве онлайн-провайдера используется Mistral AI (OpenAI-совместимый endpoint).

## 4. Аутентификация

### 4.1 Файл секретов

Путь к файлу с аутентификационными данными: `d:\projects\fullstack-demo\.secrets`

Ожидаемый формат (INI/Environment-style):

```ini
GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
MISTRAL_API_KEY=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

### 4.2 Проверки при запуске

1. Проверить наличие и читаемость файла секретов.
2. Проверить наличие `GITHUB_TOKEN` для доступа к GitHub API.
3. Проверить наличие `MISTRAL_API_KEY` (если выбран провайдер Mistral).
4. Проверить доступность Ollama (`GET /api/tags`) и Mistral AI (best-effort).

## 5. Выбор LLM-модели

При запуске утилиты:

1. Определить доступные локальные модели Ollama (`ollama.list()`).
2. Определить доступные модели Mistral AI (best-effort, если есть ключ).
3. Вывести пользователю нумерованный список доступных моделей с указанием провайдера.
4. Запросить у пользователя выбор модели (номер из списка или название).

## 6. Обработка ошибок

### 6.1 Критические ошибки (завершение работы)

| Ситуация | Действие |
|----------|----------|
| Файл секретов не найден | Вывести причину, завершить с кодом 1 |
| `GITHUB_TOKEN` отсутствует/невалиден | Вывести причину, завершить с кодом 2 |
| Нет доступных моделей (ни Ollama, ни Mistral AI) | Вывести причину, завершить с кодом 3 |
| Репозиторий не найден/нет доступа | Вывести причину, завершить с кодом 5 |
| `GITHUB_MODELS_TOKEN` отсутствует (провайдер github_models) | Вывести причину, завершить с кодом 6 |
| `GROQ_API_KEY` отсутствует (провайдер groq) | Вывести причину, завершить с кодом 7 |
| `MISTRAL_API_KEY` отсутствует (провайдер mistral) | Вывести причину, завершить с кодом 8 |
| Ошибка открытия/записи базы данных | Вывести причину, завершить с кодом 9 |

### 6.2 Временные ошибки (retry с backoff)

- Сетевые ошибки при обращении к GitHub API: до 3 попыток с exponential backoff (factor=2).
- Сетевые ошибки при обращении к LLM API: до 3 попыток с exponential backoff.
- Таймауты: 30 секунд на запрос.

### 6.3 Ошибки обработки коммитов

- При ошибке анализа отдельного коммита — записать в лог, перейти к следующему.

## 7. Анализ изменений

### 7.1 Сбор данных

1. Получить список коммитов из указанного репозитория за `GIT_DAY` дней.
2. Для каждого коммита получить:
   - SHA, автор, дата, сообщение.
   - Список изменённых файлов (status, additions, deletions, patch).
3. Исключить merge-коммиты.

### 7.2 Обработка больших diff (chunking)

Если diff коммита превышает `MAX_DIFF_CHARS_PER_CHUNK` (по умолчанию 12000 символов):
1. Разбить diff на части по границам файлов/хунков.
2. Отправить каждую часть в LLM отдельно.
3. Объединить результаты анализа частей в единое саммари коммита.

### 7.3 Дедупликация коммитов через базу данных

При каждом запуске утилита проверяет уже проанализированные коммиты в SQLite-базе (`db/`):
1. Получить список коммитов из указанного репозитория за `GIT_DAY` дней.
2. Исключить коммиты, уже присутствующие в БД (по паре `sha + repo_url`).
3. Проанализировать только новые коммиты и сохранить результат (SHA, саммари, список файлов, количество чанков) в БД.
4. Не успешный анализ коммита не записывается в БД — будет повторен при следующем запуске.
5. При старте нового сеанса удалить записи старше `DB_RETENTION_DAYS` (по умолчанию 60 дней).

### 7.4 Prompt для LLM

```
Проанализируй изменения в коммите {sha} ({author}, {date}):
{commit_message}

Изменённые файлы:
{file_list}

Patch/diff:
{diff_content}

Выдай саммари в формате:
1. Краткое описание изменений (1-3 предложения)
2. Основные изменения по файлам
3. Потенциальные риски или проблемы
4. Общая оценка качества изменений (1-5)
```

## 8. Форматы вывода

### 8.1 Консоль (rich)

- Прогресс-бар обработки коммитов.
- Для каждого коммита: список изменённых файлов + саммари (форматированный текст).
- Итоговая статистика в конце.

### 8.2 Markdown-отчёт

Файл `reports/{repo}_{date}.md`:
- Метаданные (репозиторий, период, дата генерации).
- Для каждого коммита: SHA, автор, сообщение, список файлов, саммари.
- Итоговое саммари по всем коммитам.

### 8.3 Интерактивный HTML-отчёт

Файл `reports/{repo}_{date}.html`:
- Навигация по коммитам (боковая панель).
- Подсветка синтаксиса diff (встроенный CSS/JS без внешних зависимостей).
- Фильтры по автору/дате.
- Развёрнутое/свёрнутое отображение деталей.
- Встроенные стили, работающие локально без интернета.

## 9. Артефактная память

### 9.1 Назначение

При старте новой сессии агент читает `docs/memory/STATE.md` и продолжает работу с последней точки без полного повторного анализа проекта.

### 9.2 Структура файлов

```
docs/memory/
├── STATE.md          # Текущее состояние (главный файл для чтения при старте)
├── FEATURES.md       # Реализованные фичи
├── DECISIONS.md      # Архитектурные решения
└── CHANGELOG.md      # История изменений памяти
```

### 9.3 Формат STATE.md

```markdown
# Текущее состояние проекта

## Текущая задача
{описание над чем работаем}

## Реализованы
- {фича 1}
- {фича 2}

## Архитектурные решения
- {решение 1}
- {решение 2}

## Следующие шаги
1. {шаг 1}
2. {шаг 2}

## Последнее обновление
{дата/время}
```

### 9.4 Правила работы с памятью

| Событие | Действие |
|---------|----------|
| Старт новой сессии | Прочитать STATE.md, продолжить с точки остановки |
| Реализована фича | Обновить FEATURES.md + STATE.md |
| Принято архитектурное решение | Обновить DECISIONS.md + STATE.md |
| Завершена текущая задача | Обновить "Текущая задача" в STATE.md |
| Новая задача | Записать в "Следующие шаги" при старте |
