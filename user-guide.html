1. Обзор

scan-git-push — утилита для анализа коммитов одного или нескольких git-репозиториев за указанный период. Коммиты и патчи читаются из локальных bare-зеркал (без GitHub API), саммари генерирует LLM (Ollama или Mistral AI). Отдельный режим scan ищет маркеры требований REQ-META в файлах и ведёт базу db/scan.db без вызова LLM.

2. Предусловия

Обязательно Python 3.11+ и git 2.30+

Python: python.org/downloads · git: git-scm.com. git должен быть доступен в PATH.

Опционально Файл секретов d:\projects\fullstack-demo\.secrets

Формат файла:

MISTRAL_API_KEY=ключ_из_console.mistral.ai
GITHUB_TOKEN=ghp_ваш_токен_github

MISTRAL_API_KEY нужен только при выборе Mistral AI (обязателен, если LLM.PROVIDER=mistral). GITHUB_TOKEN опционален и нужен для доступа к приватным репозиториям по HTTPS. Ollama работает без файла секретов.

Обязательно Хотя бы один LLM-провайдер:
  • Mistral AI — онлайн, OpenAI-совместимый API, есть бесплатный тариф (требуется MISTRAL_API_KEY)
  • Ollama — запущена локально на http://localhost:11434 с установленной моделью
Обязательно Git-репозитории

Поддерживаются удалённые URL (HTTPS/SSH) и локальные пути. Для каждого проекта создаётся отдельное bare-зеркало; при MIRROR_FILTER=auto удалённые репозитории клонируются частично (--filter=blob:none).

3. Установка

1 Клонировать репозиторий и перейти в каталог:

cd D:\projects\scan-git-push

2 Создать виртуальное окружение:

python -m venv .venv

3 Активировать окружение:

# Windows:
.venv\Scripts\activate

# Linux/macOS:
source .venv/bin/activate

4 Установить зависимости:

pip install -e ".[dev]"

Переключение провайдера на лету

Лимиты бесплатного тарифа Mistral AI

Бесплатный тариф Mistral AI имеет ограничения на количество запросов в минуту/день. При исчерпании лимита запросы возвращают ошибку — дождитесь сброса или выберите модель Ollama. Требуется интернет-соединение.

5. Запуск

Базовый запуск

python -m scan_git_push
python -m scan_git_push analyze --days 7

С указанием пути к конфигу

python -m scan_git_push --config C:\path\to\config.json

Процесс работы

  1. Утилита загружает конфигурацию и проверяет окружение
  2. Для каждого проекта создаёт или обновляет локальное bare-зеркало (git clone --mirror / git fetch --prune)
  3. Опрашивает Ollama и Mistral AI API и собирает доступные модели
  4. Запрашивает у пользователя выбор модели (нумерованный список — можно переключиться между провайдерами на лету)
  5. Читает коммиты за указанный период из зеркала (committer date, все ветки с дедупликацией SHA)
  6. Анализирует каждый коммит через LLM с прогресс-баром и повторными попытками
  7. Сохраняет результаты в db/analysis.db и генерирует отчёты по каждому проекту и сводный
Интерактивный выбор модели

При запуске утилита покажет нумерованный список доступных моделей. Введите номер модели и нажмите Enter.

Дедупликация коммитов (база данных)

При каждом запуске утилита проверяет уже проанализированные коммиты в SQLite-базе (db/analysis.db). Коммиты, которые были проанализированы ранее, не анализируются повторно — это предотвращает дублирование при ежедневных запусках. Записи старше ANALYSIS.DB_RETENTION_DAYS (по умолчанию 60 дней) автоматически удаляются из базы.

Генерация отчёта из базы данных (без LLM)

Команда report-from-db позволяет сгенерировать отчёты (консоль, Markdown, HTML) из уже сохранённых в БД данных, без вызова LLM:

python -m scan_git_push report-from-db --days 30
python -m scan_git_push report-from-db --project d:/projects/repo-b --json
python -m scan_git_push report-from-db --req
python -m scan_git_push report-from-db --req --project d:/projects/repo-b --json
  • --config / -c — путь к config.json
  • --days / -d — период в днях (переопределяет ANALYSIS.GIT_DAY)
  • --project / -p — ограничить отчёты указанными проектами
  • --req — вместо отчёта по коммитам собрать HTML-отчёт «Отчет по требованиям и разделам» из scan.db
  • --json — машиночитаемый результат

С --req отчёт группируется по требованию → разделу и показывает проект, ветку, коммит, файл, номер строки, коммитера и исходный маркер для каждого вхождения, а также итоги по количеству требований и разделов. Файл: reports/requirements_{YYYYMMDD}.html. analysis.db и LLM не нужны.

Это полезно, когда нужно повторно сформировать отчёт за предыдущие периоды, не тратя лимиты LLM.

Режим scan: маркеры требований без LLM

Команда scan читает tip выбранных веток и ищет канонические маркеры в файлах (SCAN.INCLUDE, по умолчанию *.txt и *.md). Результат сохраняется в db/scan.db: проекты, снимки файлов, требования, пункты и вхождения маркеров. Содержимое файлов не хранится — только SHA-256 и размер.

python -m scan_git_push scan
python -m scan_git_push scan --project d:/projects/repo-b --branch main --include "docs/**/*.html"
python -m scan_git_push scan --dry-run --strict
python -m scan_git_push --scan --json   # устаревший алиас
<!-- REQ-META id="REQ_1" point="1.1" name="Название требования" -->
  • Требования (id) глобальны: одинаковые id и point в разных проектах — это одно требование и один раздел.
  • req.is_export / point.is_export: 0 — экспорт не выполнялся, 1 — выполнен. Флаг сбрасывается в 0 при изменении требования, пункта или связанных вхождений и сохраняется при повторном сканировании без изменений.
  • В point_content зарезервированы поля numbeartefact, numbercase, numberscenario, numberstep (по умолчанию NULL); их заполнение и экспорт — будущая доработка.
  • Завершающая точка в point игнорируется: point="5.5.1." и point="5.5.1" идентичны.
  • Старые форматы (ID_REQ, ID_EXAMPLE, маркер без -->) не разбираются и дают предупреждение [WARN] legacy marker format.
  • По умолчанию сканируются только *.txt и *.md; SCAN.EXCLUDE имеет приоритет над include.
  • Symlink, submodule, LFS-указатели, бинарные и слишком большие файлы пропускаются с диагностикой.
  • --dry-run не создаёт и не изменяет БД, --force снимает зависший running-запуск, --strict возвращает код 10 при неполных маркерах.

6. Результаты

Консоль

Формированный вывод с прогресс-баром, списком файлов и саммари каждого коммита; в конце — сводка по каждому проекту и общий итог.

Markdown-отчёт

Сохраняется в reports/{repo}-{sha256(url_key)[:6]}_{date}.md — структурированный отчёт со всеми коммитами. Дополнительно создаётся сводный reports/_summary_{date}.md.

Интерактивный HTML-отчёт

Сохраняется в reports/{repo}-{sha256(url_key)[:6]}_{date}.html и reports/_summary_{date}.html — автономные файлы (не требуют интернета) с:

  • Навигацией по коммитам (боковая панель)
  • Статистикой (коммиты, файлы, LLM chunks)
  • Саммари каждого коммита и связями с требованиями

Базы данных

  • db/analysis.db — проанализированные коммиты и файлы (схема v1).
  • db/scan.db — проекты, ветки, снимки файлов, глобальные требования, пункты и вхождения маркеров; признаки экспорта и номерные поля (схема v3).
  • db/repos/ — bare-зеркала проектов; logs/ — журналы запусков.

Git-зеркала и диск

Коммиты и патчи читаются из локальных bare-зеркал в SCAN.MIRROR_DIR, а не через GitHub API. Удалённые репозитории по умолчанию клонируются частично (--filter=blob:none), поэтому первый запуск требует сети, а повторные — только git fetch. Следите за свободным местом в каталоге db/repos/.

Проверка доступности Ollama

# Проверить, что Ollama запущена:
curl http://localhost:11434/api/tags

# Список установленных моделей:
ollama list

# Установить модель (если нужно):
ollama pull llama3.1:8b

Пример файла секретов

GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
MISTRAL_API_KEY=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Безопасность

Файл .secrets добавлен в .gitignore и не коммитится в репозиторий.
