## 0. Назначение документа

Документ описывает новый режим `scan`, который сканирует файлы одного или нескольких git-репозиториев, находит маркеры требований и сохраняет в отдельную SQLite-базу `db/scan.db`:

- справочники требований и пунктов;
- снимки файлов (путь, ветка, коммит, автор, хэш содержимого);
- вхождения маркеров (пункт + файл + номер строки + исходный текст маркера).

**Содержимое файлов в БД не хранится.** Хранится только SHA-256 хэш содержимого (`blob_hash`), который позволяет определить изменение файла и пропустить повторный разбор.

Режим `scan`:

- **не вызывает LLM** и не требует выбора модели;
- **не изменяет** `analysis.db` и данные основного режима анализа коммитов;
- работает с текущими версиями файлов в выбранных ветках (tip ветки), а не с историей diff;
- обрабатывает **несколько git-проектов последовательно**, в порядке, заданном конфигурацией;
- является идемпотентным: повторный запуск не создаёт дубликатов.

| Решение | Значение |

## 1. Термины и определения

| Термин | Значение |
|--------|----------|
| Маркер | HTML-комментарий `<!-- REQ-META ... -->` с параметрами требования |
| Проект | Git-репозиторий из `SCAN.GIT_PROJECTS` |
| Ветка | Локальная ветка в зеркале репозитория (`refs/heads/*`) |
| Tip ветки | Последний коммит ветки; файлы берутся из его дерева |
| Снимок файла | Запись `file_snapshot`: проект + ветка + путь + хэш + метаданные коммита |
| `blob_hash` | SHA-256 от сырых байт blob git; единственный след содержимого в БД |
| Occurrence | Вхождение маркера в файл: `point_content` (пункт + файл + строка) |
| Reconciliation | Сверка текущего состояния с БД: архивация исчезнувших пунктов, удаление устаревших снимков |
| Зеркало | Локальная копия репозитория, созданная `git clone --mirror` |

## 2. Границы режима

### 2.1. Входит в область работ

- проверка доступности каждого git-репозитория из списка проектов;
- зеркалирование каждого проекта в локальный кэш;
- последовательная обработка проектов в порядке конфигурации;
- перечисление выбранных веток;
- чтение текстовых файлов из tip веток;
- поиск и валидация маркеров;
- ведение справочников `req`, `point` в разрезе проекта;
- хранение снимков файлов (хэши) и вхождений маркеров;
- консольный вывод, логирование, коды выхода.

### 2.2. Не входит в область работ

- вызов LLM, генерация саммари, отчёты;
- анализ diff и история коммитов;
- сканирование tags (только ветки);
- разыменование symlink, загрузка submodules и LFS-объектов;
- **хранение содержимого файлов** в БД;
- **миграции схемы** `scan.db` (БД создаётся с нуля, версия схемы `3`);
- редактирование файлов репозитория;
- автоматическое исправление маркеров;
- параллельная обработка проектов.

## 3. Конфигурация

### 3.1. Новый корневой объект `SCAN` в `config.json`

```json
{
  "SCAN": {
    "GIT_PROJECTS": [
      "https://github.com/owner/repo-a.git",
      "https://github.com/owner/repo-b.git"
    ],
    "DB_PATH": "db/scan.db",
    "MIRROR_DIR": "db/repos/",
    "MIRROR_FILTER": "auto",
    "BRANCHES": "all",
    "BRANCH_INCLUDE": [],
    "BRANCH_EXCLUDE": [],
    "INCLUDE": ["**/*.txt", "**/*.md"],
    "EXCLUDE": [],
    "EXCLUDE_SECRETS": [],
    "MAX_FILE_SIZE": 1048576,
    "ENCODING": "utf-8",
    "FALLBACK_ENCODING": "cp1251",
    "STRICT": false,
    "GC_HASHES": true,
    "LOG_PATH": "logs/scan.log"
  }
}
```

### 3.2. Семантика параметров

Все параметры режима `scan` расположены в объекте `SCAN`. В коде и документации они адресуются через точку: `SCAN.DB_PATH`, `SCAN.INCLUDE` и т. д.

| Параметр | Тип | По умолчанию | Описание |
|----------|-----|--------------|----------|
| `SCAN.GIT_PROJECTS` | list[str] | `[]` | Список git-проектов (URL или локальный путь). Пустой список → ошибка конфигурации (код `1`) |
| `SCAN.DB_PATH` | string | `db/scan.db` | Путь к БД; относительный путь разрешается от каталога `config.json` |
| `SCAN.MIRROR_DIR` | string | `db/repos/` | Каталог кэша зеркал; общий с режимом `analyze` |
| `SCAN.MIRROR_FILTER` | string | `auto` | `auto` — partial clone (`--filter=blob:none`) для удалённых URL и полный клон для локальных путей; `blob:none` — всегда partial; `none` — всегда полный клон |
| `SCAN.BRANCHES` | string \| list[str] | `all` | `all` — все ветки; `default` — ветка по умолчанию; массив имён — только указанные |
| `SCAN.BRANCH_INCLUDE` | list[str] | `[]` | Glob-шаблоны веток (с поддержкой `**`); пусто — без фильтра |
| `SCAN.BRANCH_EXCLUDE` | list[str] | `[]` | Glob-шаблоны исключаемых веток |
| `SCAN.INCLUDE` | list[str] | `["**/*.txt", "**/*.md"]` | Glob-шаблоны файлов (с поддержкой `**`); по умолчанию только текстовые и Markdown-файлы |
| `SCAN.EXCLUDE` | list[str] | `[]` | Дополнительные исключаемые каталоги/файлы; по умолчанию пусто |
| `SCAN.EXCLUDE_SECRETS` | list[str] | `[]` | Файлы, которые не читаются и не разбираются; по умолчанию пусто |
| `SCAN.MAX_FILE_SIZE` | int | `1048576` | Максимальный размер файла в байтах; больше — пропуск |
| `SCAN.ENCODING` | string | `utf-8` | Основная кодировка |
| `SCAN.FALLBACK_ENCODING` | string | `cp1251` | Резервная кодировка; пустая строка — без резерва |
| `SCAN.STRICT` | bool | `false` | Неполные маркеры приводят к коду выхода `10` |
| `SCAN.GC_HASHES` | bool | `true` | Удалять неиспользуемые записи `file_hash` после успешного сканирования |
| `SCAN.LOG_PATH` | string | `logs/scan.log` | Файл лога; относительный путь разрешается от каталога `config.json` |

Правила применения шаблонов:

- шаблоны применяются к repo-relative POSIX-пути (`docs/requirements.md`);
- `**` соответствует любому числу каталогов, включая ноль, поэтому `**/*.md` соответствует и файлам в корне репозитория;
- шаблон без `/` сопоставляется с именем файла (`*.md` эквивалентно `**/*.md`);
- сопоставление выполняется **без учёта регистра** (`.MD`, `.TXT` тоже подходят);
- exclude-шаблоны имеют приоритет над include;
- `SCAN.EXCLUDE_SECRETS` имеет приоритет над `SCAN.INCLUDE`: файл, попавший под секретный шаблон, не читается вообще.

### 3.3. Совместимость с существующим `config.json`

- `SCAN.GIT_PROJECTS` — единственный источник списка проектов; ключ `GIT_PROJECT` удалён.
- Параметр `--project` (можно несколько раз) полностью заменяет `SCAN.GIT_PROJECTS`.
- Локальный путь в `SCAN.GIT_PROJECTS` разрешается от каталога `config.json`.
- `GIT_DAY` в режиме `scan` **игнорируется**.
- `ANALYSIS.DB_PATH`, `ANALYSIS.DB_RETENTION_DAYS` относятся к `analysis.db` и в `scan` не используются.
- Секции `SCAN`, `ANALYSIS`, `LLM` сосуществуют в одном `config.json`; `scan` читает только `SCAN`, `analyze` — `ANALYSIS` и `LLM`.
- Валидатор URL расширяется: допускаются `https://`, `ssh://`, `git://`, `file://` и локальные пути.
- Валидация `SCAN` выполняется моделью Pydantic (`ScanSettings`); неизвестные ключи внутри `SCAN` считаются ошибкой конфигурации (код `1`), чтобы опечатки не игнорировались молча.
- `SCAN.MIRROR_DIR` общий с `analyze`: одно зеркало на проект переиспользуется обоими режимами.
- `url_key` вычисляется одинаково в `scan.db` и `analysis.db` (remote — `host/path` без схемы, учётных данных и `.git`; local — абсолютный POSIX-путь), что делает возможным `ATTACH` и `LINK_REQUIREMENTS`.

## 4. CLI

### 4.1. Канонический запуск

```bash
python -m scan_git_push scan [OPTIONS]
```

### 4.2. Алиас для обратной совместимости

```bash
python -m scan_git_push --scan [OPTIONS]
```

Оба варианта должны приводить к одному и тому же поведению. Алиас `--scan` считается устаревшим, но поддерживается.

### 4.3. Опции

| Опция | Описание |
|-------|----------|
| `--config PATH` | Путь к `config.json` |
| `--project URL` | Проект; можно указывать несколько раз. Заменяет `SCAN.GIT_PROJECTS` |
| `--branch NAME` | Ветка; можно указывать несколько раз |
| `--all-branches` | Эквивалент `SCAN.BRANCHES=all` |
| `--include GLOB` | Дополнительный include-шаблон; дополняет `SCAN.INCLUDE`; можно несколько |
| `--exclude GLOB` | Дополнительный exclude-шаблон; дополняет `SCAN.EXCLUDE`; можно несколько |
| `--max-file-size BYTES` | Переопределить лимит размера файла |
| `--dry-run` | Полный скан без записи в БД |
| `--force` | Игнорировать активный `running`-запуск и пометить его `failed` |
| `--strict` | Неполные маркеры → код выхода `10` |
| `--json` | Машиночитаемый вывод |
| `--no-color` | Отключить цвета |
| `--verbose` | DEBUG-вывод в консоль |

### 4.4. Правила выбора веток

Правила применяются к каждому проекту независимо (набор веток у проектов может различаться).

1. Если заданы `--branch`, используются только они.
2. Иначе, если задан `--all-branches`, используются все ветки.
3. Иначе используется `SCAN.BRANCHES`:
   - `all` — все `refs/heads/*` (значение по умолчанию);
   - `default` — ветка по умолчанию (`git symbolic-ref --short HEAD` в зеркале);
   - массив/список имён — только указанные.
4. К выбранному набору применяются `SCAN.BRANCH_INCLUDE` / `SCAN.BRANCH_EXCLUDE`.
5. Служебные ссылки (`HEAD`, `origin/HEAD`) исключаются.
6. Ветки, указанные в `--branch`, но отсутствующие в проекте: предупреждение и пропуск ветки; если у проекта не осталось ни одной ветки — проект считается обработанным с предупреждением.

### 4.5. Порядок обработки проектов

1. Проекты обрабатываются строго последовательно, в порядке `SCAN.GIT_PROJECTS` (или `--project`).
2. Дубликаты в списке устраняются по `url_key` с сохранением первого вхождения.
3. Один проект — одно зеркало — одна запись `git_project` — отдельные записи `scan_run`.
4. Ошибка одного проекта не прерывает обработку остальных (кроме фатальных ошибок БД и схемы).

### 4.6. Отчёт по требованиям и разделам

```bash
python -m scan_git_push report-from-db [--config PATH] [--project URL ...] --req [--json]
```

- `--req` строит автономный HTML-отчёт только по данным `scan.db`; `analysis.db` и LLM не используются.
- Отчёт включает только активные требования и разделы (`req.status = 1`, `point.status = 1`).
- Группировка: требование → раздел → вхождения; разделы сортируются естественным образом (`5.2` перед `5.10`).
- Для каждого вхождения выводятся проект (`git_project.url`), ветка, коммит, путь файла, номер строки, коммитер и исходный маркер.
- Файл: `reports/requirements_YYYYMMDD.html` в `OUTPUT_DIR`.
- `--project` ограничивает отчёт выбранными проектами (по `url_key`).
- Итоги: количество требований и количество разделов.
- Без `--req` команда работает как раньше: отчёт по коммитам из `analysis.db`.

## 5. Алгоритм работы

### Шаг 0. Подготовка окружения

1. Загрузить и провалидировать конфигурацию, включая объект `SCAN`.
2. Проверить наличие `git` (`git --version`). Если git недоступен — сообщение и код `1`.
3. Разрешить `SCAN.DB_PATH`, `SCAN.MIRROR_DIR`, `SCAN.LOG_PATH` относительно каталога `config.json`.
4. Создать каталоги при необходимости.
5. Открыть `scan.db` (только при обычном запуске) и включить PRAGMA:

   ```sql
   PRAGMA foreign_keys = ON;
   PRAGMA journal_mode = WAL;
   PRAGMA synchronous = NORMAL;
   PRAGMA busy_timeout = 5000;
   ```

   Назначение `synchronous = NORMAL`: в режиме WAL это оптимальный баланс между скоростью записи и сохранностью данных — транзакции не теряются при падении процесса, риск потери ограничен последними коммитами при отключении питания. Значение `FULL` избыточно для сканирования, `OFF` недопустимо.

   `PRAGMA synchronous` устанавливается сразу после открытия соединения, **до** начала любой транзакции: SQLite возвращает ошибку `Safety level may not be changed inside a transaction`. `journal_mode = WAL` — постоянная настройка файла БД, `foreign_keys` и `synchronous` — настройки соединения и должны задаваться при каждом подключении.

   При `--dry-run`: если БД существует — открыть в режиме чтения и проверить версию схемы; если БД нет — не создавать её.

6. Проверить версию схемы:
   - БД отсутствует → создать схему (раздел 7) и записать версию `3` (только при обычном запуске);
   - версия `3` → продолжить работу;
   - версия отличается от `3` (в том числе `0`, `1`, `2` или `> 3`) или схема повреждена → сообщение и код `12`.
   Миграции не выполняются: БД создаётся с нуля. Если `scan.db` уже существует с другой версией, её нужно удалить вручную.

### Шаг 1. Формирование списка проектов

1. Взять список из `--project` (если задан), иначе из `SCAN.GIT_PROJECTS`.
2. Нормализовать каждый элемент (раздел 5.1) и вычислить `url_key`.
3. Удалить дубликаты по `url_key`, сохранив порядок.
4. Если итоговый список пуст — сообщение об ошибке конфигурации и код `1`.
5. Вывести список проектов и их количество.

### Шаг 2. Обработка проекта (цикл по списку)

Для каждого проекта выполняются подшаги 2.1–2.6. Проекты обрабатываются последовательно.

#### 2.1. Проверка доступности репозитория

1. Выполнить `git ls-remote --heads <url>` с:
   - `GIT_TERMINAL_PROMPT=0`;
   - таймаутом 30 секунд;
   - до 3 попыток с exponential backoff (factor 2).
2. При успехе (только при обычном запуске):
   - найти или создать запись в `git_project` по `url_key`;
   - установить `status = 1` (реактивация архивного проекта);
   - обновить `author`, если он определяется из URL;
   - обновить `updated_at`.
   При `--dry-run` запись в `git_project` не выполняется.
3. Перед созданием новой записи `scan_run` проверить активные запуски этого проекта:
   - `running` моложе 24 часов → считается, что сканирование уже выполняется; проект пропускается, ошибка фиксируется (обходится флагом `--force`);
   - `running` старше 24 часов → пометить как `failed`.
   Затем создать запись `scan_run` со `status = 'running'` (только при обычном запуске).
4. При ошибке доступа:
   - вывести причину (DNS, таймаут, 401/403, 404, нет прав);
   - зафиксировать проект как неуспешный;
   - перейти к следующему проекту (обработка остальных продолжается).
5. Пустой репозиторий (нет веток) — не ошибка: вывести предупреждение, обновить `scan_run` до `success` и перейти к следующему проекту.

#### 2.2. Подготовка зеркала

1. Каталог зеркала: `<SCAN.MIRROR_DIR>/<repo-name>-<sha256(url_key)[:10]>.git` — отдельный для каждого проекта, общий с режимом `analyze`.
2. Если зеркала нет — `git clone --mirror [--filter=blob:none] <url> <path>` в зависимости от `SCAN.MIRROR_FILTER`.
3. Если зеркало есть — `git remote update --prune`.
4. Ошибка clone/fetch — проект неуспешен, переход к следующему проекту.
5. Запрещён shallow clone (`--depth`), чтобы корректно определять последний коммит файла. Partial clone (`blob:none`) допустим: отсутствующие blob-объекты подгружаются git автоматически при `git cat-file --batch`.
6. Зеркала разных проектов не пересекаются и не переиспользуются.

#### 2.3. Определение набора веток

1. Получить список: `git for-each-ref --format='%(refname:short)' refs/heads`.
2. Применить правила раздела 4.4.
3. Если итоговый список пуст — предупреждение, проект считается успешным без изменений.

#### 2.4. Обход веток и файлов

Для каждой ветки проекта:

1. Получить дерево: `git ls-tree -r -l -z <branch>`.
2. Оставить только регулярные файлы (`100644`, `100755`).
3. Пропустить:
   - symlink (`120000`);
   - submodule (`160000`);
   - файлы, не подходящие под `SCAN.INCLUDE` (по умолчанию — всё, кроме `*.txt` и `*.md`);
   - файлы, подходящие под `SCAN.EXCLUDE`;
   - файлы из `SCAN.EXCLUDE_SECRETS` (не читаются и не разбираются);
   - файлы больше `SCAN.MAX_FILE_SIZE`.
4. Прочитать blob пачкой через `git cat-file --batch`. Содержимое используется **только в памяти** и не сохраняется в БД.
5. Определить бинарность: наличие `\x00` в первых 8192 байтах → пропуск с предупреждением.
6. Декодировать:
   - UTF-8 (с BOM или без);
   - при ошибке — `SCAN.FALLBACK_ENCODING`;
   - при повторной ошибке — пропуск с предупреждением.
7. Обнаружить LFS-указатель (`version https://git-lfs.github.com/spec/v1`) → пропуск с предупреждением.
8. Вычислить `sha256` от **сырых байт blob** (не от декодированного текста) и запомнить `size_bytes`.
9. Определить последний коммит, затронувший путь:
   - `commit_sha`, `author`, `committer`;
   - для каждого файла в пределах ветки;
   - при невозможности определить — `NULL`.
10. Разобрать маркеры (раздел 6), собрать:
    - список валидных вхождений;
    - список ошибок с путём, строкой и именем отсутствующего/некорректного параметра.
11. Если `blob_hash` не изменился с прошлого успешного сканирования, `parser_version` совпадает и для файла уже есть актуальные `point_content` — не переразбирать маркеры, использовать существующие вхождения. Содержимое в этом случае можно не декодировать (достаточно хэша), но `size_bytes` должно совпадать.

#### 2.5. Запись в БД

Шаг выполняется только при обычном запуске. При `--dry-run` шаг 2.5 пропускается, БД не изменяется.

Все изменения по одному проекту выполняются в одной транзакции `BEGIN IMMEDIATE`:

1. UPSERT `file_hash` по `hash`:
   - `INSERT INTO file_hash(hash, size_bytes) VALUES (?, ?) ON CONFLICT(hash) DO NOTHING`;
   - при конфликте `size_bytes` не меняется (хэш однозначно определяет размер);
   - содержимое файла не записывается ни при каких настройках.
2. UPSERT `file_snapshot` по `(git_project_id, branch, path)`:
   - обновить `commit_sha`, `author`, `committer`, `blob_hash`, `encoding`, `scanned_at`, `parser_version`.
3. UPSERT `req` по `code` (глобально, без привязки к проекту):
   - новый код → `name` из маркера или `"Требование без наименования"`;
   - существующий код и непустой `name` отличается → обновить `name`, залогировать предупреждение о конфликте;
   - существующий код и `name` отсутствует → сохранить текущее имя.
4. UPSERT `point` по `(req_id, point)`; установить `status = 1`.
5. Заменить вхождения для изменённых/новых файлов:
   - `DELETE FROM point_content WHERE file_id = ?`;
   - вставить актуальные `point_content` с `line_no` и `raw_marker`.
   Для неизменённых файлов (пункт 11 шага 2.4) вхождения не трогать.
6. Reconciliation проекта (только для веток, обработанных без критических ошибок):
   - для каждой полностью просканированной ветки удалить `file_snapshot` проекта, путь которых отсутствует в наборе успешно обработанных путей этой ветки (каскадно удалятся `point_content`). Это правило покрывает удалённые файлы, смену расширения, попадание под `SCAN.EXCLUDE`/`SCAN.EXCLUDE_SECRETS`, бинарность и превышение размера;
   - если `SCAN.BRANCHES=all`, удалить снимки веток проекта, которых больше нет в репозитории;
   - `point.status = 0`, если для пункта не осталось ни одного `point_content` (в любом проекте);
   - `req.status = 0`, если у требования не осталось активных пунктов (в любом проекте);
   - `point.status = 1`, `req.status = 1` при повторном появлении.
   При частичном сбое устаревшие записи проблемной ветки не удаляются.
7. Обновить `scan_run` этого проекта, созданный в подшаге 2.1:
   - `finished_at`, `status` (`success` / `partial` / `failed`);
   - `branches` (JSON-массив);
   - счётчики `files_scanned`, `files_skipped`, `markers_found`, `errors_count`;
   - `message` (краткое описание).
8. `COMMIT`.

При любой ошибке БД — `ROLLBACK` по текущему проекту, сообщение и код `9` (фатально, обработка остальных проектов прекращается).

#### 2.6. Очистка неиспользуемых хэшей

Выполняется **один раз** после успешной обработки всех проектов, а не после каждого проекта (хэш может использоваться другим проектом):

```sql
DELETE FROM file_hash
WHERE hash NOT IN (SELECT blob_hash FROM file_snapshot);
```

Выполняется только при `SCAN.GC_HASHES=true` и только если все проекты обработаны без фатальных ошибок.

## 6. Формат маркеров

### 6.1. Канонический формат (единственный поддерживаемый)

```html
<!-- REQ-META id="REQ_5" point="4.1" name="Требование 5" -->
```

Правила:

- маркер занимает **одну строку**;
- обязательный префикс `REQ-META`;
- обязательное закрытие `-->`;
- параметры в формате `key="value"`;
- порядок параметров произвольный;
- ключи фиксированы и регистрозависимы: `id`, `point`, `name`;
- `id` и `point` обязательны;
- `name` опционален;
- пустое значение приравнивается к отсутствию;
- дубликат ключа — ошибка;
- неизвестный ключ — предупреждение;
- экранирование кавычек: `\"` внутри значения;
- максимальная длина строки маркера — 4096 символов.

Грамматика:

```ebnf
marker      = ws "<!--" ws "REQ-META" ws attr *( ws attr ) ws "-->" ws ;
attr        = key ws "=" ws '"' value '"' ;
key         = "id" | "point" | "name" ;
value       = *( escaped-char | unescaped-char ) ;
escaped-char   = "\" ( '"' | "\" ) ;
unescaped-char = ? любой символ, кроме '"', "\" и перевода строки ? ;
ws          = ? пробелы и табуляция ? ;
```

Парсер обязан:

- принимать атрибуты в любом порядке;
- отклонять неизвестные ключи с предупреждением;
- отклонять дубликаты ключей с ошибкой;
- не зависеть от регистра ключей (ключи фиксированы: `id`, `point`, `name`);
- сохранять значения как есть, без нормализации регистра; исключение — завершающая точка в `point` отбрасывается.

Другие форматы маркеров **не поддерживаются**. Строки, содержащие `ID_REQ`, `ID_EXAMPLE` или конструкцию без закрывающего `-->`, маркерами не считаются и обрабатываются как обычные HTML-комментарии. Для диагностики по таким строкам выводится `[WARN] legacy marker format` (предупреждение, на код выхода не влияет).

### 6.2. Валидация значений

| Параметр | Правило |
|----------|---------|
| `id` | `^[A-Za-z][A-Za-z0-9_.-]{0,63}$` |
| `point` | после отбрасывания завершающих точек: `^\d+(\.\d+){0,7}$`; `5.5.1.` → `5.5.1` |
| `name` | до 255 символов, без управляющих символов; пустое → отсутствует |

### 6.3. Разбор

1. Читать файл построчно.
2. Если строка содержит `<!--` и `REQ-META` — применить канонический разбор.
3. Иначе, если строка содержит `<!--`:
   - это обычный HTML-комментарий, не ошибка;
   - в `--verbose` вывести `[INFO]` о пропуске.
4. Для каждого найденного маркера:
   - проверить обязательные параметры;
   - проверить форматы;
   - проверить дубликаты ключей;
   - при ошибке — сформировать запись об ошибке с `path`, `line`, `missing`/`invalid`;
   - при успехе — сформировать occurrence.
5. Несколько маркеров в одном файле обрабатываются независимо.
6. Повторяющиеся пары `(id, point)` **не являются ошибкой и не являются дубликатами**:
   - в одном файле на разных строках — сохраняется столько occurrences, сколько найдено;
   - в разных файлах — каждое вхождение сохраняется отдельно;
   - в разных проектах — это независимые требования (раздел 7.4).
   Единственное ограничение — уникальность `(point_id, file_id, line_no)`: две разные строки одного файла всегда дают разные записи.

При изменении правил разбора необходимо увеличить константу `SCAN_PARSER_VERSION` в коде. Это форсирует переразбор всех файлов и исключает использование устаревших `point_content`.

### 6.4. Конфликты имён

Если для одного `id` **в разных проектах или в разных файлах** указаны разные `name`:

- обрабатывать в детерминированном порядке: проекты — в порядке `SCAN.GIT_PROJECTS`, ветки — по алфавиту, пути — по алфавиту, строки — по возрастанию;
- победителем считается последнее обработанное непустое значение;
- в консоль и лог выводится предупреждение с обоими значениями и путями.

Одинаковые `id` в разных проектах — это **одно и то же требование**: `req.code` глобально уникален, а вхождения связываются с проектами через `file_snapshot`.

## 7. Логическая модель данных

### 7.1. Принципы

- Таблицы и колонки — `snake_case`.
- `status` — `INTEGER` (`0`/`1`), не `BOOLEAN`.
- Все временные метки — ISO 8601 UTC (`YYYY-MM-DDTHH:MM:SS.sssZ`).
- Внешние ключи включены; поведение `ON DELETE` задано явно.
- **Содержимое файлов не хранится.** Хранятся только `blob_hash`, размер и метаданные снимка.
- Требования глобальны: `req.code` уникален в разрезе **всех** проектов; одинаковые `code` в разных проектах — одно требование.
- Одинаковые `blob_hash` в разных ветках и проектах хранятся один раз (`file_hash`).
- Справочники `req` и `point` не удаляются, а архивируются через `status = 0`.
- Снимки файлов отражают текущее состояние и могут удаляться при reconciliation.

### 7.2. DDL

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;

CREATE TABLE IF NOT EXISTS schema_version (
    version     INTEGER NOT NULL,
    applied_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
);

CREATE TABLE IF NOT EXISTS git_project (
    id          INTEGER PRIMARY KEY,
    url         TEXT    NOT NULL,
    url_key     TEXT    NOT NULL UNIQUE,
    author      TEXT,
    status      INTEGER NOT NULL DEFAULT 1 CHECK (status IN (0, 1)),
    created_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    updated_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
);

-- Требование уникально в разрезе всех проектов.
CREATE TABLE IF NOT EXISTS req (
    id              INTEGER PRIMARY KEY,
    code            TEXT    NOT NULL UNIQUE,
    name            TEXT    NOT NULL DEFAULT 'Требование без наименования',
    status          INTEGER NOT NULL DEFAULT 1 CHECK (status IN (0, 1)),
    is_export       INTEGER NOT NULL DEFAULT 0 CHECK (is_export IN (0, 1)),
    created_at      TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    updated_at      TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
);

CREATE TABLE IF NOT EXISTS point (
    id          INTEGER PRIMARY KEY,
    req_id      INTEGER NOT NULL REFERENCES req(id) ON DELETE CASCADE,
    point       TEXT    NOT NULL,
    status      INTEGER NOT NULL DEFAULT 1 CHECK (status IN (0, 1)),
    is_export   INTEGER NOT NULL DEFAULT 0 CHECK (is_export IN (0, 1)),
    created_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    updated_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    UNIQUE (req_id, point)
);

-- Реестр хэшей содержимого. Содержимое файлов намеренно не хранится.
CREATE TABLE IF NOT EXISTS file_hash (
    hash        TEXT    PRIMARY KEY CHECK (length(hash) = 64),
    size_bytes  INTEGER NOT NULL CHECK (size_bytes >= 0),
    created_at  TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
);

CREATE TABLE IF NOT EXISTS file_snapshot (
    id              INTEGER PRIMARY KEY,
    git_project_id  INTEGER NOT NULL REFERENCES git_project(id) ON DELETE CASCADE,
    branch          TEXT    NOT NULL,
    path            TEXT    NOT NULL,
    commit_sha      TEXT,
    author          TEXT,
    committer       TEXT,
    blob_hash       TEXT    NOT NULL REFERENCES file_hash(hash) ON DELETE RESTRICT,
    encoding        TEXT    NOT NULL DEFAULT 'utf-8',
    parser_version  INTEGER NOT NULL DEFAULT 1,
    scanned_at      TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    UNIQUE (git_project_id, branch, path)
);

-- Вхождение маркера. Одинаковые (point_id, file_id) на разных строках допустимы.
-- Номерные поля заполняются будущей доработкой; по умолчанию NULL.
CREATE TABLE IF NOT EXISTS point_content (
    id               INTEGER PRIMARY KEY,
    point_id         INTEGER NOT NULL REFERENCES point(id) ON DELETE CASCADE,
    file_id          INTEGER NOT NULL REFERENCES file_snapshot(id) ON DELETE CASCADE,
    line_no          INTEGER NOT NULL CHECK (line_no > 0),
    raw_marker       TEXT    NOT NULL,
    numbeartefact    TEXT    DEFAULT NULL,
    numbercase       TEXT    DEFAULT NULL,
    numberscenario   TEXT    DEFAULT NULL,
    numberstep       TEXT    DEFAULT NULL,
    created_at       TEXT    NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    UNIQUE (point_id, file_id, line_no)
);

CREATE TABLE IF NOT EXISTS scan_run (
    id              INTEGER PRIMARY KEY,
    git_project_id  INTEGER NOT NULL REFERENCES git_project(id) ON DELETE CASCADE,
    started_at      TEXT    NOT NULL,
    finished_at     TEXT,
    status          TEXT    NOT NULL CHECK (status IN ('running', 'success', 'partial', 'failed')),
    branches        TEXT    NOT NULL DEFAULT '[]',
    files_scanned   INTEGER NOT NULL DEFAULT 0,
    files_skipped   INTEGER NOT NULL DEFAULT 0,
    markers_found   INTEGER NOT NULL DEFAULT 0,
    errors_count    INTEGER NOT NULL DEFAULT 0,
    message         TEXT
);

CREATE INDEX IF NOT EXISTS idx_point_req
    ON point(req_id);

CREATE INDEX IF NOT EXISTS idx_point_content_point
    ON point_content(point_id);

CREATE INDEX IF NOT EXISTS idx_point_content_file
    ON point_content(file_id);

CREATE INDEX IF NOT EXISTS idx_file_snapshot_project_branch
    ON file_snapshot(git_project_id, branch);

CREATE INDEX IF NOT EXISTS idx_scan_run_project_started
    ON scan_run(git_project_id, started_at);

-- Инвалидация экспорта: смысловое изменение сбрасывает is_export в 0.
-- Обновление только is_export (результат экспорта) триггеры не запускает.
CREATE TRIGGER IF NOT EXISTS trg_req_is_export
AFTER UPDATE OF code, name, status ON req
FOR EACH ROW
WHEN NEW.code IS NOT OLD.code
  OR NEW.name IS NOT OLD.name
  OR NEW.status IS NOT OLD.status
BEGIN
    UPDATE req SET is_export = 0 WHERE id = NEW.id AND is_export = 1;
END;

CREATE TRIGGER IF NOT EXISTS trg_point_is_export
AFTER UPDATE OF point, status ON point
FOR EACH ROW
WHEN NEW.point IS NOT OLD.point
  OR NEW.status IS NOT OLD.status
BEGIN
    UPDATE point SET is_export = 0 WHERE id = NEW.id AND is_export = 1;
END;

CREATE TRIGGER IF NOT EXISTS trg_point_content_insert
AFTER INSERT ON point_content
FOR EACH ROW
BEGIN
    UPDATE point SET is_export = 0 WHERE id = NEW.point_id AND is_export = 1;
END;

CREATE TRIGGER IF NOT EXISTS trg_point_content_update
AFTER UPDATE OF point_id, line_no, raw_marker,
    numbeartefact, numbercase, numberscenario, numberstep ON point_content
FOR EACH ROW
BEGIN
    UPDATE point SET is_export = 0
    WHERE id IN (OLD.point_id, NEW.point_id) AND is_export = 1;
END;

CREATE TRIGGER IF NOT EXISTS trg_point_content_delete
AFTER DELETE ON point_content
FOR EACH ROW
BEGIN
    UPDATE point SET is_export = 0 WHERE id = OLD.point_id AND is_export = 1;
END;
```

### 7.3. Назначение таблиц

| Таблица | Назначение |
|---------|------------|
| `git_project` | Репозитории, с которыми работает режим `scan` |
| `req` | Глобальные требования (`id` маркера) и их наименования; уникальны по `code`; `is_export` — признак выполненного экспорта |
| `point` | Пункты требований (`point`) в разрезе требования; `is_export` — признак выполненного экспорта |
| `file_hash` | Реестр SHA-256 хэшей и размеров; содержимого не содержит |
| `file_snapshot` | Текущее состояние файла в ветке проекта |
| `point_content` | Вхождение маркера: пункт + файл + строка + исходный текст; номерные поля (`numbeartefact`, `numbercase`, `numberscenario`, `numberstep`) |
| `scan_run` | Аудит запусков и статистика по каждому проекту |
| `schema_version` | Версия схемы (контроль совместимости) |

### 7.4. Область уникальности и трактовка совпадений

Принято решение: `req.code` уникален **в разрезе всех проектов** (`UNIQUE(code)`).

Обоснование: в разных репозиториях могут одновременно существовать маркеры с одинаковыми `id` и `point` — это нормальная ситуация, так как работы ведутся в рамках одних и тех же требований. Поэтому требование и его раздел — общие, а привязка к конкретному проекту, ветке, коммиту и файлу хранится во вхождении `point_content` → `file_snapshot` → `git_project`.

Следствия:

| Ситуация | Трактовка |
|----------|-----------|
| Одинаковые `(id, point)` в разных проектах | Одно глобальное требование и один раздел; отдельные вхождения в каждом проекте |
| Одинаковые `(id, point)` в разных файлах одного проекта | Одно требование и один пункт; два разных вхождения (`point_content`) |
| Одинаковые `(id, point)` в одном файле на разных строках | Одно требование и один пункт; несколько вхождений |
| Полностью идентичная строка `(point_id, file_id, line_no)` | Невозможна: строка одна, защищено `UNIQUE` |

### 7.4.1. Признак экспорта и номерные поля

`req.is_export` и `point.is_export` — целые `0/1`, по умолчанию `0`:

| Значение | Трактовка |
|----------|-----------|
| `0` | Экспорт не выполнялся (или данные изменились после экспорта) |
| `1` | Экспорт выполнен |

Правила инвалидации (реализованы триггерами раздела 7.2):

| Событие | Сбрасывается |
|---------|--------------|
| Новое требование | `req.is_export = 0` (значение по умолчанию) |
| Изменение `req.code`, `req.name`, `req.status` | `req.is_export = 0` |
| Новый пункт | `point.is_export = 0` (значение по умолчанию) |
| Изменение `point.point` или `point.status` | `point.is_export = 0` |
| Вставка, изменение или удаление `point_content`, связанного с пунктом | `point.is_export = 0` |

Триггеры срабатывают только при реальном изменении (`NEW.x IS NOT OLD.x`), поэтому повторное сканирование без изменений сохраняет `is_export = 1`. Обновление только самого `is_export` (результат будущего экспорта) флаг не сбрасывает.

Номерные поля `point_content` — `numbeartefact` («Номер артефакта»), `numbercase` («Номер тест-кейса»), `numberscenario` («Номер сценария»), `numberstep` («Номер шага сценария») — текстовые, по умолчанию `NULL`. Алгоритм их заполнения и экспорт — будущая доработка; текущий `scan` значения не изменяет.

### 7.5. Версия схемы

- Текущая версия схемы: `3`.
- БД `db/scan.db` создаётся с нуля; миграции не предусмотрены.
- При старте:
  - файла БД нет → создать схему (раздел 7.2) и вставить `schema_version = 3`;
  - файл есть, версия `3`, таблицы на месте → продолжить работу;
  - файл есть, но таблица `schema_version` отсутствует или пуста → код `12`;
  - версия `≠ 3` (в том числе `0`, `1`, `2` или `> 3`) → код `12`;
  - ошибка чтения схемы → код `12`.
- `schema_version` используется только как защита от запуска на несовместимой БД. Её наличие позволяет в будущем добавить миграции без изменения текущей логики.
- Сброс БД: остановить процесс, удалить `db/scan.db` (и файлы `-wal` / `-shm`) и запустить сканирование заново. Автоматического удаления БД нет.
- Первичное наполнение не требуется: все таблицы создаются пустыми, кроме служебной `schema_version`.

## 8. Обработка ошибок и коды выхода

### 8.1. Критические ошибки

| Ситуация | Код |
|----------|-----|
| Ошибка конфигурации, отсутствует `git`, неверные пути, пустой список проектов | `1` |
| Нет/невалиден токен, если он требуется для доступа | `2` |
| Нет доступных LLM-моделей (зарезервировано основным ТЗ) | `3` |
| Неверные аргументы CLI | `4` |
| Репозиторий не найден / нет доступа / ошибка clone/fetch (все проекты) | `5` |
| Нет токена GitHub Models (зарезервировано) | `6` |
| Нет токена Groq (зарезервировано) | `7` |
| Нет токена Mistral (зарезервировано) | `8` |
| Ошибка открытия/записи/блокировки `scan.db` | `9` |
| Неполные маркеры при `--strict` | `10` |
| Частичный сбой обработки (часть проектов, веток или файлов) | `11` |
| Несовместимая/повреждённая схема `scan.db` | `12` |

### 8.2. Частичный сбой

Частичным сбоем считается ситуация, когда:

- не удалось получить доступ к одному из проектов;
- не удалось прочитать отдельный файл;
- не удалось обработать отдельную ветку;
- git-команда вернула ошибку по конкретному объекту;
- проект пропущен из-за активного `running`-запуска.

При этом:

- остальные проекты/файлы/ветки обрабатываются;
- ошибки выводятся в консоль и лог;
- `scan_run.status = 'partial'` для затронутого проекта;
- код выхода `11`.

Штатные пропуски (бинарный файл, превышение размера, неподдерживаемая кодировка, LFS, symlink, submodule, секретный шаблон, файл вне `SCAN.INCLUDE`) **не являются** частичным сбоем и не влияют на код выхода.

При `--strict` валидные данные всё равно записываются в БД; код `10` сигнализирует о наличии ошибок валидации, а не отменяет результат.

### 8.3. Повторные попытки

- `git ls-remote`, `clone`, `fetch`: 3 попытки, exponential backoff factor 2, таймаут 30 секунд.
- Ошибки чтения отдельных blob: 1 повтор, затем частичный сбой.
- Ошибки БД не повторяются; выполняется `ROLLBACK`.

## 9. Транзакционность и идемпотентность

1. Транзакция выполняется **на каждый проект**: `BEGIN IMMEDIATE` … `COMMIT`. Сбой одного проекта не откатывает результаты остальных.
2. При ошибке БД — `ROLLBACK` по текущему проекту, код `9`, обработка прекращается.
3. Повторный запуск без изменений:
   - не создаёт новых `req`/`point` (глобально);
   - не дублирует `point_content`;
   - не создаёт новых `file_hash`;
   - обновляет `scanned_at` и `scan_run`;
   - не меняет `blob_hash`.
4. Параллельные запуски:
   - `PRAGMA busy_timeout = 5000`;
   - `PRAGMA synchronous = NORMAL` (WAL) — достаточная надёжность при сохранении скорости;
   - при блокировке — сообщение и код `9`;
   - активный `scan_run` со `status='running'` моложе 24 часов — проект пропускается, код `11` (обходится `--force`);
   - не допускается два одновременных писателя.
5. `--dry-run`:
   - выполняет доступ к git и разбор файлов;
   - может обновлять локальные зеркала репозиториев;
   - не открывает БД на запись;
   - не создаёт `scan.db`;
   - выводит ту же сводку, что и обычный запуск.
6. При любой фатальной ошибке после создания `scan_run` (подшаг 2.1) — best-effort обновить `scan_run.status = 'failed'` и `finished_at` отдельной транзакцией. Это относится и к ошибкам clone/fetch, и к ошибкам БД.
7. Очистка `file_hash` выполняется после обработки всех проектов и не входит в транзакцию отдельного проекта.

## 10. Обработка файлов

### 10.1. Что сканируется

- только tip выбранных веток каждого проекта;
- только регулярные текстовые файлы;
- по умолчанию — только файлы с расширением `.txt` и `.md` (`SCAN.INCLUDE`);
- файлы, не подходящие под `SCAN.EXCLUDE` и `SCAN.EXCLUDE_SECRETS`;
- размер не больше `SCAN.MAX_FILE_SIZE`.

Сканируются **все** подходящие файлы tip, а не только изменённые в последнем коммите: маркер мог быть добавлен давно, и файл с тех пор не менялся. Фильтрация по diff/истории не применяется.

Ограничение по расширениям снижает объём чтения и исключает случайный разбор кода, конфигураций и бинарных артефактов. При необходимости список расширений расширяется через `SCAN.INCLUDE`.

### 10.2. Что пропускается

| Категория | Причина | Сообщение |
|-----------|---------|-----------|
| Не подходит под `SCAN.INCLUDE` | расширение/путь вне списка | не выводится (DEBUG) |
| Бинарный файл | `\x00` в первых 8192 байтах | `[SKIP] binary` |
| Большой файл | размер > лимита | `[SKIP] too large` |
| Неподдерживаемая кодировка | не UTF-8 и не fallback | `[SKIP] encoding` |
| LFS-указатель | содержимое — pointer | `[SKIP] lfs pointer` |
| Symlink | режим `120000` | `[SKIP] symlink` |
| Submodule | режим `160000` | `[SKIP] submodule` |
| Секретный файл | `SCAN.EXCLUDE_SECRETS` (по умолчанию пусто) | `[SKIP] secret pattern` |

Если ранее сканировавшийся файл теперь пропускается (переименован в другое расширение, стал бинарным, превысил лимит, попал в секретный шаблон), его `file_snapshot` удаляется при reconciliation, а связанные пункты могут быть переведены в архив. Это ожидаемое поведение: снимок отражает только актуальное сканируемое состояние.

### 10.3. Удалённые и переименованные файлы

- Файл, отсутствующий в tip, не сканируется; его `file_snapshot` удаляется при reconciliation.
- Переименования не отслеживаются: путь берётся из tip, `commit_sha` — последний коммит, затронувший текущий путь.
- Ограничение документируется в разделе 16.

### 10.4. Хэш содержимого

- Алгоритм: SHA-256.
- Вход: сырые байты blob из git.
- Формат: 64 hex-символа в нижнем регистре.
- Хэш не зависит от CRLF/LF-конверсии и кодировки.
- Хэш — единственный след содержимого файла в БД; само содержимое не сохраняется.
- Хэш используется для:
  - дедупликации `file_hash` между ветками и проектами;
  - обнаружения изменения файла;
  - пропуска повторного разбора неизменённых файлов.

### 10.5. Кодировка

- Основная: UTF-8 (с BOM и без).
- Резервная: `SCAN.FALLBACK_ENCODING` (по умолчанию `cp1251`).
- BOM удаляется перед разбором.
- В `file_snapshot.encoding` сохраняется фактическая кодировка (`utf-8`, `utf-8-sig`, `cp1251`).
- При ошибке декодирования файл пропускается с предупреждением.
- Декодированный текст живёт только в памяти в пределах обработки файла.

## 11. Вывод в консоль и логирование

### 11.1. Формат сообщений

```text
[OK]    repo-a  docs/requirements.md:12  id=REQ_5 point=4.1 name="Требование 5"
[ERROR] repo-a  docs/requirements.md:20  missing: point
[WARN]  repo-a  docs/other.md:7          name conflict id=REQ_5: "Требование 5" vs "Требование 5 (уточн.)"
[SKIP]  repo-a  docs/dump.txt            encoding
[INFO]  repo-a  README.md                no REQ-META markers
```

- `[OK]` — зелёный;
- `[ERROR]` — красный;
- `[WARN]` — жёлтый;
- `[SKIP]` — dim;
- `[INFO]` — обычный.

Сообщение `[INFO]` о файле без маркеров выводится только при `--verbose`; в остальных случаях оно пишется в лог на уровне `DEBUG`.

Цвета — только дополнение. При `--no-color`, `NO_COLOR` или отсутствии TTY выводится plain text.

### 11.2. Итоговая сводка

Сводка выводится по каждому проекту, затем общий итог.

```text
=== https://github.com/owner/repo-a ===
Branches:       main, develop
Files scanned:  1240
Files skipped:  18
Markers found:  356
REQ created:    42
REQ updated:    3
POINT created:  210
POINT archived: 4
Errors:         2
Duration:       00:01:23
Status:         success

=== https://github.com/owner/repo-b ===
Branches:       main
Files scanned:  310
Files skipped:  2
Markers found:  58
REQ created:    0
REQ updated:    13
POINT created:  44
POINT archived: 0
Errors:         0
Duration:       00:00:14

--- Total ---
Projects:       2 (success: 2, partial: 0, failed: 0)

```

`markers_found` — количество валидных вхождений; невалидные маркеры и ошибки чтения учитываются в `errors`/`errors_count`.

`REQ created` / `REQ updated` — счётчики **текущего прохода по проекту**, а не размер глобального справочника. Требование глобально (`UNIQUE(code)`): если `id` уже встречался в другом проекте в этом же запуске или в предыдущем запуске, новый `req` не создаётся. Поэтому `REQ created: 0` у второго проекта — нормальная ситуация, а не ошибка. Общее число требований в БД — `SELECT COUNT(*) FROM req` (сумма по проектам не равна ему).

### 11.3. Логирование

- `loguru`;
- файл `SCAN.LOG_PATH`, UTF-8;
- rotation `10 MB`, retention `30 days`;
- уровень файла — `DEBUG`, консоли — `INFO` (или `DEBUG` при `--verbose`);
- каждая запись содержит `url_key` проекта;
- токены, URL с учётными данными и содержимое файлов в лог не попадают.

## 12. Безопасность

1. **Содержимое файлов.**
   - Содержимое не сохраняется в БД ни при каких настройках: хранятся только `blob_hash`, размер и вхождения маркеров.
   - Декодированный текст обрабатывается в памяти и освобождается после разбора файла.
   - Файлы из `SCAN.EXCLUDE_SECRETS` не читаются и не разбираются (по умолчанию список пуст; для приватных репозиториев рекомендуется заполнить).
   - Поскольку по умолчанию сканируются только `*.txt` и `*.md`, риск попадания ключей и бинарных секретов минимален.
2. **Токены.**
   - Учётные данные удаляются из URL перед сохранением и логированием.
   - Для аутентификации использовать `GIT_ASKPASS` или `http.extraHeader`, не URL с токеном.
3. **Пути.**
   - Допускаются только repo-relative POSIX-пути.
   - Отклоняются абсолютные пути, `..`, NUL-байты.
4. **Регулярные выражения.**
   - Построчный разбор.
   - Ограничение длины строки 4096 символов.
   - Квантификаторы ограничены.
5. **SQL.**
   - Только параметризованные запросы.
6. **Содержимое репозитория.**
   - Не выполнять хуки, скрипты и команды из репозитория.
   - `GIT_TERMINAL_PROMPT=0`.
   - Все git-команды выполняются без shell; аргументы передаются списком.
   - URL и имена веток валидируются перед передачей в git.
7. **Файл БД.**
   - На POSIX — права `0600`.
   - На Windows — ограничение ACL по возможности; документировать.
8. **Логи.**
   - Не логировать содержимое файлов.
   - Не логировать токены и URL с учётными данными.
9. **Маркеры.**
   - `raw_marker` хранится как есть и может содержать `name`; не размещать в `name` секретные данные.

## 13. Производительность

### 13.1. Рекомендуемая реализация доступа к git

1. Один раз клонировать зеркало на проект: `git clone --mirror`.
2. Обновлять: `git fetch --prune --all`.
3. Дерево ветки: `git ls-tree -r -l -z <branch>`.
4. Содержимое: `git cat-file --batch`.
5. Последний коммит файла: один проход `git log --format=... --name-only <branch>` или кэшируемый `git log -1 -- <path>`.

Не использовать GitHub Contents API для массового чтения файлов: лимит 5000 запросов/час и ограничение 1 MiB на файл делают его непригодным для больших репозиториев.

### 13.2. Ориентиры

| Сценарий | Цель |
|----------|------|
| 10 000 файлов, 50 веток, один проект, первый запуск | ≤ 10 минут |
| 5 проектов по 1 000 файлов, 5 веток | ≤ 10 минут суммарно |
| Повторный запуск без изменений | ≤ 2 минуты |
| Размер `scan.db` | определяется числом снимков и вхождений; содержимое не хранится, поэтому БД на порядки меньше, чем при хранении файлов |

### 13.3. Оптимизации

- пропуск повторного разбора при совпадении `blob_hash` и `parser_version` (содержимое даже не декодируется);
- `SCAN.INCLUDE` по умолчанию ограничен `*.txt` и `*.md` — резко снижает объём чтения;
- `file_hash` хранит одинаковый контент один раз;
- пакетные вставки в одной транзакции на проект;
- `PRAGMA journal_mode = WAL` + `PRAGMA synchronous = NORMAL`;
- индексы из раздела 7;
- лимит размера файла;
- последовательная обработка проектов исключает конкуренцию за CPU, диск и канал.

## 14. Критерии приёмки

### 14.1. База данных

- [ ] При отсутствии `db/scan.db` создаётся файл со всеми таблицами, FK, индексами, триггерами инвалидации экспорта и `schema_version = 3`.
- [ ] При версии схемы `≠ 3` или повреждённой схеме — сообщение и код `12`.
- [ ] Включены четыре PRAGMA: `foreign_keys = ON`, `journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 5000`.
- [ ] Каскадные удаления работают: удаление `git_project` удаляет его `point_content`, `file_snapshot`, `scan_run`; глобальные `req`/`point` архивируются через `status`.
- [ ] `status` хранится как `0/1`, значения вне диапазона отклоняются.
- [ ] `is_export` хранится как `0/1`, по умолчанию `0`; значения вне диапазона отклоняются.
- [ ] В таблице `file_hash` нет колонки содержимого; в БД отсутствуют байты файлов.
- [ ] `req` имеет `UNIQUE(code)`; одинаковые `code` в разных проектах — одно требование.
- [ ] `point_content.numbeartefact`, `numbercase`, `numberscenario`, `numberstep` допускают `NULL` и по умолчанию `NULL`.
- [ ] Повторный запуск не создаёт дубликатов `req`, `point`, `point_content`, `file_snapshot`, `file_hash`.

### 14.2. Маркеры

- [ ] Канонический маркер `<!-- REQ-META ... -->` распознаётся.
- [ ] Строки с `ID_REQ`, `ID_EXAMPLE` и вариант без `-->` маркерами не считаются; выводится `[WARN] legacy marker format`, ошибкой не является.
- [ ] Маркер без `id` или `point` — ошибка с путём, строкой и именем параметра.
- [ ] Обычный `<!-- TODO -->` не считается ошибкой.
- [ ] Несколько маркеров в одном файле обрабатываются все.
- [ ] Повторяющиеся `(id, point)` в разных файлах — не дубликаты; сохраняются все вхождения.
- [ ] Повторяющиеся `(id, point)` в одном файле на разных строках — не дубликаты; сохраняются все вхождения.
- [ ] Некорректный `id`/`point` — ошибка валидации.
- [ ] Завершающая точка в `point` игнорируется: `5.5.1.` сохраняется как `5.5.1`; `point="."` — ошибка.

### 14.3. Сканирование

- [ ] Сканируются tip выбранных веток каждого проекта.
- [ ] `SCAN.BRANCHES=default|all|<array>` работает для каждого проекта независимо.
- [ ] По умолчанию сканируются только `*.txt` и `*.md`; прочие файлы не читаются.
- [ ] Include/exclude-шаблоны применяются; exclude имеет приоритет.
- [ ] Бинарные, большие, не-UTF-8, LFS, symlink, submodule файлы пропускаются с сообщением.
- [ ] Удалённые файлы удаляются из `file_snapshot` при reconciliation.
- [ ] `commit_sha`, `author`, `committer` заполняются для существующих файлов.
- [ ] `blob_hash` считается по сырым байтам и не зависит от CRLF.

### 14.4. Несколько проектов

- [ ] `SCAN.GIT_PROJECTS` с двумя и более значениями обрабатывается последовательно в заданном порядке.
- [ ] Для каждого проекта создаётся отдельное зеркало в `SCAN.MIRROR_DIR`.
- [ ] Для каждого проекта создаётся отдельная запись `scan_run`.
- [ ] Одинаковые `(id, point)` в разных проектах дают **одно глобальное** `req` и один `point`; вхождения остаются раздельными по проектам.
- [ ] Ошибка доступа к одному проекту не прерывает обработку остальных; код `11`.
- [ ] Если недоступны все проекты — код `5`.
- [ ] `--project` заменяет список проектов и может указываться несколько раз.
- [ ] Пустой `SCAN.GIT_PROJECTS` и отсутствие `--project` приводят к коду `1`; fallback на `GIT_PROJECT` отсутствует.

### 14.5. Идемпотентность и reconciliation

- [ ] Повторный запуск без изменений не меняет `req`, `point`, `point_content`, `file_hash`.
- [ ] Повторный запуск без изменений сохраняет `req.is_export` и `point.is_export` равными `1`.
- [ ] Изменение `req.code/name/status` сбрасывает `req.is_export` в `0`.
- [ ] Изменение `point.point/status`, вставка, изменение или удаление `point_content` сбрасывает `point.is_export` в `0`.
- [ ] При удалении маркера `point.status` становится `0`; при исчезновении всех пунктов `req.status = 0`.
- [ ] При повторном появлении маркера `status` возвращается в `1`.
- [ ] При `SCAN.BRANCHES=all` удалённые ветки удаляются из `file_snapshot` своего проекта.
- [ ] Reconciliation одного проекта не затрагивает данные других проектов.
- [ ] `--dry-run` не изменяет БД и не создаёт `scan.db`.

### 14.6. Ошибки и коды выхода

- [ ] Недоступны все репозитории — код `5`.
- [ ] Ошибка БД — код `9`.
- [ ] Неполные маркеры при `--strict` — код `10`.
- [ ] Частичный сбой — код `11`.
- [ ] Несовместимая схема — код `12`.
- [ ] Штатные пропуски не влияют на код выхода.

### 14.7. Интеграция

- [ ] `python -m scan_git_push scan` работает.
- [ ] `python -m scan_git_push --scan` работает как алиас.
- [ ] В режиме `scan` не вызывается LLM и не запрашивается выбор модели.
- [ ] `analysis.db` не создаётся и не изменяется.
- [ ] Конфигурация читается из вложенного объекта `SCAN`; параметры `SCAN_*` в корне не поддерживаются.
- [ ] `--json` выдаёт валидный JSON с массивом `projects` и объектом `totals`.
- [ ] `--no-color` отключает цвета.
- [ ] Лог пишется в `logs/scan.log`.

## 16. Ограничения и допущения

1. Сканируется только tip веток; история не анализируется.
2. Tags не сканируются.
3. Переименования не отслеживаются; коммит определяется по текущему пути.
4. Submodules, symlinks и LFS-объекты не разыменовываются.
5. По умолчанию сканируются только `*.txt` и `*.md`; остальные расширения требуют изменения `SCAN.INCLUDE`.
6. Содержимое файлов не сохраняется; восстановить текст файла из БД невозможно.
7. `req.code` уникален в разрезе всех проектов; одинаковые `id` в разных проектах — одно требование.
8. Одинаковые `(id, point)` в разных файлах и на разных строках — не дубликаты.
9. Поддерживается только канонический формат маркера `REQ-META`; прежние форматы не распознаются.
10. Один писатель SQLite; параллельные запуски блокируются.
11. Проекты обрабатываются последовательно, без параллелизма.
12. Режим `scan` не вызывает LLM.
13. `GIT_DAY` не используется.
14. Для приватных репозиториев требуется настроенный git-доступ; токен не хранится в БД.
15. Маркеры внутри fenced code blocks Markdown обрабатываются как обычный текст. Для примеров в документации используйте экранирование или отдельный префикс.
16. Требуется `git` версии 2.30 или новее.
17. Завершающая точка в `point` не является значимой и отбрасывается при разборе.

## Приложение A. Примеры маркеров

### A.1. Канонический (поддерживается)

```html
<!-- REQ-META id="REQ_5" point="4.1" name="Требование 5" -->
```

### A.2. Невалидные

```html
<!-- REQ-META id="REQ_5" name="Без пункта" -->
<!-- REQ-META point="4.1" -->
<!-- REQ-META id="REQ 5" point="4.1" -->
<!-- REQ-META id="REQ_5" point="4.1" id="REQ_6" -->
<!-- TODO: доработать -->
```

Ожидаемое поведение: первые четыре строки — ошибки валидации (отсутствует параметр, неверный формат, дубликат ключа); последняя — обычный комментарий, не ошибка.

### A.3. Не поддерживается

```html
<!-- "ID_REQ" = "REQ_5" "POINT" = "4.1" "NAME" = "Требование 5" -->
<!-- "ID_EXAMPLE" = "REQ_5" "POINT" = "4.1" "NAME" = "Требование 5" -->
<!-- "ID_EXAMPLE" = "REQ_5" "POINT" = "4.1" "NAME" = "Требование 5">
```

Ожидаемое поведение: маркерами не считаются; выводится `[WARN] legacy marker format`; на код выхода не влияет. Требуется перевод файлов на канонический формат.

## Приложение B. Пример SQL-запросов

### B.1. Активные требования и пункты по проекту

```sql
SELECT gp.url, r.code, r.name, p.point
FROM req r
JOIN point p ON p.req_id = r.id
JOIN point_content pc ON pc.point_id = p.id
JOIN file_snapshot fs ON fs.id = pc.file_id
JOIN git_project gp ON gp.id = fs.git_project_id
WHERE r.status = 1 AND p.status = 1
ORDER BY gp.url, r.code, p.point;
```

### B.2. Вхождения маркеров с файлами

```sql
SELECT
    gp.url,
    r.code,
    p.point,
    fs.branch,
    fs.path,
    pc.line_no,
    pc.raw_marker
FROM point_content pc
JOIN point p ON p.id = pc.point_id
JOIN req r ON r.id = p.req_id
JOIN file_snapshot fs ON fs.id = pc.file_id
JOIN git_project gp ON gp.id = fs.git_project_id
ORDER BY gp.url, r.code, p.point, fs.branch, fs.path, pc.line_no;
```

### B.3. Файлы и их хэши

```sql
SELECT gp.url, fs.branch, fs.path, fh.hash, fh.size_bytes
FROM file_snapshot fs
JOIN file_hash fh ON fh.hash = fs.blob_hash
JOIN git_project gp ON gp.id = fs.git_project_id
ORDER BY gp.url, fs.branch, fs.path;
```

### B.4. Одинаковые требования в разных проектах

```sql
SELECT DISTINCT r.code, gp.url, r.name
FROM req r
JOIN point p ON p.req_id = r.id
JOIN point_content pc ON pc.point_id = p.id
JOIN file_snapshot fs ON fs.id = pc.file_id
JOIN git_project gp ON gp.id = fs.git_project_id
WHERE r.code = ?
ORDER BY gp.url;
```

### B.5. Статистика последнего запуска по каждому проекту

```sql
SELECT gp.url, sr.*
FROM scan_run sr
JOIN git_project gp ON gp.id = sr.git_project_id
WHERE sr.id IN (
    SELECT id FROM scan_run sr2
    WHERE sr2.git_project_id = sr.git_project_id
    ORDER BY started_at DESC
    LIMIT 1
)
ORDER BY gp.url;
```
